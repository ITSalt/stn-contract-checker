# STN Contract Checker

Прототип для специалиста по закупкам: загружаете TXT-файлы договоров поставки, допсоглашений и писем и
получаете таблицу «номер — поставщик — сумма — срок поставки» на дату проверки. У каждого значения
есть проверяемое основание: имя файла, точная цитата и переход к абзацу исходного текста. Если значения
нет, показывается «нет данных», если ответ ненадёжен — «требует проверки». Значения не придумываются.

Тестовое задание Product Owner, Semantic TextNavigator. Записка PO (пользователь, вопросы клиенту,
допущения, метрики, архитектура, решения, масштабирование, следующие шаги) — в [docs/NOTE.md](docs/NOTE.md).
Материалы эксперимента (план, решения, ревью, приёмка тремя клиентами, снимки версий) — docs/experiment/.

**[Иллюстрированный дневник разработки](https://itsalt.github.io/stn-contract-checker/)** — полный лонгрид
с 61 скриншотом и просмотрщиком с увеличением. Для чтения без интернета скачайте репозиторий и откройте
`docs/longread/index.html`; папка `assets/` должна оставаться рядом. [Подробнее](docs/longread/README.md).

## Установка и запуск

Требования: Node.js 22 LTS и npm. Бэкенда, базы данных, ключей API
и платных подписок нет: всё работает в браузере, документы никуда не отправляются.

```bash
npm ci            # или npm i
npm run dev       # http://localhost:5173
```

Сборка для статического хостинга: `npm run build` (результат — в `dist/`), просмотр сборки —
`npm run preview`.

## Проверки

| Команда | Что проверяет |
|---------|---------------|
| `npm test` | vitest, 295 тестов. Движок: эталон на `documents/` при дате 10.03.2026, устойчивость к новому договору, переименованию файлов, порядку загрузки, дате проверки, переформулировкам с ловушками; каждая цитата — точная подстрока файла. Интерфейс (Testing Library + jsdom): загрузка, таблица, панель основания, вопросы, фильтры, дата. Компоненты дизайн-системы. |
| `npm run typecheck` | `tsc --noEmit` по `src`, `e2e` и конфигам |
| `npm run e2e:shots` | Playwright: настоящий браузер проходит сценарий закупщика на файлах `documents/`. На каждом шаге сначала проверяется ключевое значение, потом снимается экран. Отсутствующий элемент роняет тест, а не даёт пустой снимок. |

`npm run e2e:shots` сам поднимает dev-сервер на порту `E2E_PORT` (по умолчанию 5291, порт должен быть
свободен) и пишет 10 снимков 1440×900 в `SHOTS_DIR` (по умолчанию `artifacts/screenshots/`, каталог в
`.gitignore`). Имена снимков постоянные, поэтому версии можно сравнивать рядом:

`01-empty`, `02-uploaded-table`, `03-evidence-stn101-delivery`, `04-pending-changes`,
`05-q1-stn101-delivery`, `06-q2-stn102-amount`, `07-q3-stn103-amount`, `08-q4-before-april`,
`09-checkdate-28-02`, `10-width-1024`.

Шаг `10-width-1024` дополнительно проверяет, что у таблицы и страницы нет горизонтальной прокрутки на
ширине 1024 px. Нужен Chromium для Playwright 1.63.0: если его нет, поставьте
`npx playwright install chromium`.

## Пример: сценарий закупщика и четыре вопроса

1. Откройте приложение и загрузите все файлы из `documents/`: кнопкой «Выбрать файлы», перетаскиванием
   или кнопкой «Загрузить учебный комплект» (это те же 6 файлов из `public/samples/`, они проходят тот
   же разбор).
2. В списке «Документы» видно, как распознан каждый файл: договор, подписанное допсоглашение, проект,
   письмо или «не распознан», статус подписания и к какому договору он относится.
3. Дата проверки по умолчанию 10.03.2026. В таблице три договора:

   | Договор | Поставщик | Сумма | Срок поставки | Статус строки |
   |---------|-----------|-------|---------------|---------------|
   | STN-101 | ООО «Вектор Прибор» | 1 380 000 ₽ (изменено `02_amendment_signed.txt`, было 1 200 000 ₽) | 30.04.2026 (изменено, было 15.04.2026) | есть несогласованные изменения (проект `06`) |
   | STN-102 | ООО «Контур Электро» | 840 000 ₽ | 20.03.2026 | есть несогласованные изменения (письмо `05`) |
   | STN-103 | ООО «ПромСнаб Сервис» | нет данных | 30.04.2026 | нет данных: сумма |

4. Кнопки быстрых вопросов (тексты из задания) и ожидаемые ответы:

   | Вопрос | Ответ приложения |
   |--------|------------------|
   | Какой срок поставки действует по договору STN-101 на 10 марта 2026 года? | 30.04.2026, изменено `02_amendment_signed.txt` (было 15.04.2026); есть несогласованное изменение (проект на 10.05.2026) |
   | Какова сумма договора STN-102? | 840 000 ₽ (источник `03_contract.txt`); аванс 252 000 ₽ суммой не считается |
   | Какова сумма договора STN-103? | нет данных — в договоре сказано, что стоимость не указана (`04_contract.txt`, цитата «Числовое значение стоимости в тексте договора не указано.»); лимит 600 000 ₽ суммой не считается |
   | По каким договорам поставка запланирована раньше 1 апреля 2026 года и есть ли несогласованные изменения срока? | только STN-102 (20.03.2026); несогласованное изменение срока — 27.03.2026 из письма поставщика; таблица отфильтрована |

   Номер договора и даты в вопросах — параметры, ответ всегда считается по загруженным документам.
   Если договора нет среди загруженных, ответ — «Нет данных: договор … не найден».
5. Смените дату проверки на 28.02.2026: допсоглашение ещё не вступило в силу, у STN-101 снова
   1 200 000 ₽ и 15.04.2026, а изменения из допсоглашения переходят в «Сведения для проверки».
6. Фильтры над таблицей: «срок поставки раньше [дата]», «есть несогласованные изменения», поиск по
   номеру или поставщику.

## Как устроено основание

- Текст каждого файла делится на абзацы `p1…pn` (непустые строки) с номером пункта (`2.1`) и
  смещениями в исходном тексте.
- Клик по любому значению в таблице открывает боковую панель «Основание»: значение и его статус, имя
  файла, номер абзаца и точная цитата. Тесты проверяют, что `text.slice(start, end) === quote`.
- Если значение изменено допсоглашением, видны обе редакции: действующая (из допсоглашения) и
  исходная (из договора).
- «Показать в тексте» прокручивает к полному тексту документа и подсвечивает абзац (якорь
  `<файл>-<pN>`), а цитата в нём выделена.
- Блок «Сведения для проверки (не действуют)» показывает изменения, которые условий не меняют: письма,
  проекты, допсоглашения без подписи обеих сторон и подписанные, но не вступившие в силу. У каждого
  есть причина и цитата.

Правило задания: условия меняет только допсоглашение, подписанное обеими сторонами и вступившее в силу
не позже даты проверки. Тип документа и приоритет определяются по тексту; имена файлов, даты в них и
порядок загрузки на результат не влияют.

Статусы значения: `ok` — значение и цитата найдены; `no_data` («нет данных») — значения нет, цитата
показывает, где об этом сказано, если такое место есть; `needs_review` («требует проверки») — значение
нельзя надёжно определить. Последнее бывает, когда два действующих допсоглашения меняют одно поле,
подпись неясна, нет даты вступления в силу, документ не связан с договором, договор загружен дважды
или пункт найден, но не распознан.

## Известные ограничения

- **Только TXT.** Файлы других форматов не загружаются, приложение называет пропущенные. PDF, DOCX и
  OCR не поддерживаются.
- **Формат документов — как у учебного набора.**
  - Нужны: заголовок «ДОГОВОР … № <номер>» или «… К ДОГОВОРУ <номер>», строка «Статус:», нумерованные
    пункты «2.1.», формулировки «Пункт N договора изложить в следующей редакции: «…»», «Пункт N
    договора в редакции … изложить», «увеличить … до Y» (берётся Y, а не прирост) и «вступает в силу
    <дата>».
  - Сумма и срок ищутся по смыслу предложения, а не по номеру пункта и не по «первому числу в тексте».
    Аванс, доля платежа, лимит, потолок «не более», неустойка, срок оплаты и дата приёмки отбрасываются.
  - Документ другого формата не угадывается: его тип «не распознан», а поля получают «нет данных» или
    «требует проверки».
- **Даты** — `ДД.ММ.ГГГГ` или «5 июня 2026». Срок, заданный периодом («в течение 30 дней»), уходит в
  «требует проверки».
- **Суммы** — цифрами с «руб.», «рублей» или «₽»: «1.200.000 руб.», «1 200 000 ₽», «тыс./млн руб.».
  Сумма прописью без цифр и сумма в валюте (не рубли) уходят в «требует проверки», пересчёта по курсу
  нет.
- **Несколько допсоглашений.** Если несколько действующих допсоглашений меняют одно поле, применяется
  последнее по дате вступления в силу. Договор, подписанный позже даты проверки, получает «требует
  проверки».
- **Связь документов** — только по номеру договора в тексте. Письмо, проект или допсоглашение, где
  названо несколько разных договоров («по договорам STN-301 и STN-302»), не привязывается ни к одному:
  документ и каждый названный договор получают «требует проверки», изменения из документа не
  применяются и не показываются как предложения.
- **Масштаб** — десятки документов в одной вкладке. Хранения, истории и прав доступа нет: всё живёт в
  памяти страницы до перезагрузки.
- **Заглушек нет.** Кнопка «Загрузить учебный комплект» загружает копию `documents/` из
  `public/samples/`, и эти файлы проходят тот же разбор, что и загруженные вручную. Готовых ответов в
  коде нет.

## Риски, которые остаются

- Дата прописью («тридцатого апреля») не распознаётся: срок получает «нет данных», даты нужно писать
  цифрами или «5 июня 2026».
- Ширина 375 px не поддерживается: интерфейс рассчитан на десктоп от 1024 px, на телефоне появляется
  горизонтальная прокрутка.
- Панель «Основание» модальная: пока она открыта, таблица и кнопки недоступны, её нужно закрыть (Esc).
- Поиск работает только по номеру договора и поставщику, по сумме и сроку не ищет.


## Отчёт о вайбкодинге

**Инструмент.** Claude Code (модель Claude Opus) по схеме «один оркестратор + сессии-исполнители». Сессия
оркестратора разбила задачу на пакеты работ с критериями приёмки, раздала их трём параллельным
сессиям (движок и интерфейс, дизайн-система, записка) и проверяла каждый PR независимыми
агентами-рецензентами в одноразовом клоне. Рецензенты писали свои варианты документов, делали мутации
кода и снимали экраны. Merge выполнял оркестратор по решению владельца; код в `main` попадал только
через PR с ревью.

**Характерные запросы к ИИ:**

1. Стартовый промпт сессии: «Прочитай `…/WP-APP-01-engine.md` и выполни. Ветка
   `vypolnenie-testovogo/wp-app-01-engine` от `origin/main`, PR в main, не мержить. По готовности —
   сообщение координатору». В самом пакете были ловушки задания в критериях: «Никогда не брать соседние
   суммы (аванс, лимит) и сроки (оплата, приёмка) — по смыслу пункта, а не „первое число в тексте“» и
   «На демо изменят одно поле и загрузят новый договор того же формата — вшивать номера, суммы, даты и
   имена файлов нельзя».
2. Возврат на доработку по итогам ревью: «„2.2. Первый платёж составляет 30% цены договора, т.е.
   252 000 рублей“ → 252000 ok … Предложения с долей/потолком/платежом не дают значение — needs_review
   с цитатой или пропуск; тесты на оба».
3. Требование к браузерному сценарию: «на каждом шаге проверяет ключевое значение (expect) и лишь потом
   снимает экран; отсутствующий элемент — падение теста, а не пустой снимок».

**Ошибки ИИ и как их поймали:**

- **Самая важная.** Движок прошёл все свои 53 теста и эталон, но независимый рецензент написал
  10 переформулировок пунктов, и 3 из них дали неверное значение со статусом `ok`:
  - «Первый платёж … 30% цены договора, т.е. 252 000 рублей» → 252 000 как сумма договора;
  - «не более 600 000» → сумма;
  - «Поставленный товар оплачивается не позднее 10.04.2026» → срок поставки.

  Исправлено в пересдаче: тема предложения (платёж, доля, потолок, оплата или приёмка, в том числе в
  глагольной форме) отбрасывает значение или переводит его в «требует проверки». На каждую формулировку
  есть тест, мутации кода роняют тесты. Вывод: тесты, написанные тем же ИИ, проверяют то, о чём он
  подумал. Нужна независимая проверка чужими примерами.
- **Регулярное выражение.** В выражении с двумя альтернативными группами ИИ брал `m[1]`, и номер
  договора из письма терялся. Поймал первый же прогон на `documents/` (TypeError).
- **Порядок проверок.** Проверка «подписано после даты проверки» стояла раньше проверки «дата
  вступления в силу», и причина на 28.02.2026 получалась неверной. Поймал тест на дату 28.02.2026.
- **Интерфейс.** Панель «Основание» сначала прокручивалась целиком, и значение с цитатой уходили за
  экран. Тесты этого не видят, поймал снимок `03`. Затем рецензент нашёл, что неподписанное
  допсоглашение подписывалось «Подписанное допсоглашение» и что переход к абзацу не виден. Исправлено,
  на оба случая есть тесты, e2e проверяет, что абзац в окне.
- **Окружение.** Последняя версия Playwright требовала браузер, которого не было на машине. Поймал
  `playwright install --dry-run`, версия закреплена на 1.63.0.

**Приёмка тремя клиентами.** После сдачи продукт проверили три независимых клиента: 48 сценариев в
браузере. Два FAIL нашёл конкурентный клиент: «увеличить … на 180 000» бралось как сумма договора
вместо итоговой, а второе допсоглашение молча пропускалось. Оба исправлены, на каждый есть тест. Вопрос 1
больше не переставляет дату проверки молча: показывает «Дата проверки изменена на 10.03.2026» и кнопку
«Вернуть».

Проверку в браузере снимали на каждой версии интерфейса одним и тем же сценарием `npm run e2e:shots`,
поэтому одноимённые снимки разных версий можно сравнить. Сами снимки в репозиторий не входят.

**Фактические затраты.** Начало — 30.10.2026 08:40 UTC, окончание — 13:56 UTC (последний коммит этого
README). Итого 5 ч 16 мин от начала при бюджете 4 ч: после 4 часов шли приёмка тремя клиентами,
исправления и проверка на чистой машине. Работа шла параллельно: оркестратор, три сессии-исполнителя и
